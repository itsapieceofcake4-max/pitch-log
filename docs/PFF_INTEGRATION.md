# PFF FC（FIFA World Cup 2022）を Pitch Log で扱う

引き継ぎ資料 `引き継ぎ_PFFデータ_PitchLogアプリ読み込み.md` に対する実装記録。

---

## 使い方

```bash
cd C:\Users\User\Desktop\pitch-log
streamlit run app_26.py
```

> **`pff/` や `rugby/` を編集したら Streamlit を再起動すること。**
> Streamlit はメインスクリプトを再実行するが、import 済みモジュールは
> `sys.modules` に古いまま残るため、追加した関数が `ImportError` になる。
> `.streamlit/config.toml` に `server.folderWatchList = ["pff", "rugby"]` を
> 入れて自動リロードするようにしてあるが、確実なのは `Ctrl + C` からの再起動。

1. **① シーンを選ぶ** — 日本戦 4 試合のゴール・決定機・シュート・ライン突破の
   一覧から、解析したいシーンを選ぶ
2. **② 俯瞰で確認** — 2D ピッチ上で 22 人＋ボールの動きを再生して確認
3. **③ 書き出す** — Export_GSA 形式（126列）で CSV 出力。app_22 / app_23 が
   そのまま読める

CLI からも使える。

```bash
python -m pff.scenes --min-priority 60      # シーン候補の一覧
python -m pff.quality --game 3854           # トラッキング品質の実測
python -m pff.batch --out C:\pff_scenes     # 正解例をまとめて書き出す
```

### 正解例をまとめて作る（`pff/batch.py`）

1 シーンずつ画面で選ぶのは確認向き。GSA の正解パターンを何本もそろえる
段階では一括で出したほうが早い。

```bash
python -m pff.batch --out C:\pff_scenes                    # 日本戦の全ゴール
python -m pff.batch --out C:\pff_scenes --kinds ゴール 決定機
python -m pff.batch --out C:\pff_scenes --game 3854 --window 12
```

**窓の長さは既定で自動選択**（`--window auto`）。ボール捕捉率が 95% を保てる
最長の窓を選ぶので、デッドタイムを掴まない。出力フォルダには

- `{game}_{選手}_{秒}.csv` … 425 指標つき（1 シーン 1 ファイル）
- `{game}_{選手}_{秒}_legend.csv` … スロット対応表
- `_index.csv` … 一覧（窓・捕捉率・行数・結果）
- `_指標データ辞書.csv` … 列の説明（全ファイル共通）

が入る。日本戦の全ゴールで **11 件・14MB**。

#### 実行結果（日本戦 4 試合の全ゴール 15 件）

| 結果 | 件数 | 内訳 |
|---|---|---|
| 成功 | 11 | 窓は 5〜30 秒が自動で選ばれた |
| 失敗 | 4 | **10506 の PK 戦（120 分以降）** |

> **10506（日本 vs クロアチア）のトラッキングは 8103 秒（延長終了）まで**で、
> PK 戦（8247〜8472 秒）は収録されていない。データ側の制約であり、
> 変換の不具合ではない。

> `3821` グンドアンのゴール（32:35）は **どの窓でもボール捕捉率 0%**。
> 出力自体は成功するが、ボール由来の指標（距離・前進・保持者）が全欠測に
> なるため `_index.csv` に「要確認」と記録される。

## Task 0 — アプリの入力仕様（実測）

### app_23 は SPADL を使っていない

引き継ぎ資料は「app_23 が VAEP なら SPADL 形式の可能性が高い」としていたが、
**`socceraction` も SPADL も一切使っていない**。app_22 と同じ Export_GSA CSV を
土台に VAEP パネルを足した構成。**変換先は 1 つだけでよい。**

### Export_GSA 形式

| 項目 | 実測値 |
|---|---|
| 形状 | 300行 × 126列（サンプル） |
| 粒度 | 1行 = 1フレーム |
| 座標系 | **正規化 [0, 1]**（メートルではない。内部で ×105 / ×68 して距離計算） |
| fps | **固定ではない**。`detect_fps()` が Time 列の差分から自動判定 |
| 攻撃方向 | Home が x=1 方向。Away は xT マップを左右反転して適用 |

```
Frame, Time, Match_Time_sec
Ball_X, Ball_Y, Ball_GridID, Ball_ZoneID, Ball_xT
Home_P1_X, Home_P1_Y, Home_P1_GridID, Home_P1_ZoneID, Home_P1_xT   … P11まで
Away_P1_… … P11まで
Home_MAX_xT, Home_SUM_xT, Away_MAX_xT, Away_SUM_xT
is_line_breaking_pass, lbp_passer, lbp_receiver, lbp_nearby_def_count
```

### 引き継ぎ資料の想定と違った点（いずれも有利な方向）

1. **10fps 固定ではない。** fps は自動判定されるので **30fps のまま投入できる**
2. **11人固定ではない。** `^Home_P(\d+)_X$` の正規表現で動的に検出する
3. **GridID / xT / ZoneID は自作不要。** `xt_pipeline_22` が X/Y から計算する

## Task 2 — データ構造（実測。引き継ぎ資料との差分に注意）

| 項目 | 実測 | 資料の記載 |
|---|---|---|
| fps | **29.97**（Metadata の `fps` に明記） | 約29.97 ✓ |
| 座標 | 中心原点メートル。x が長辺(±52.5)、y が短辺(±34) | ✓ |
| **選手の `speed`** | **存在しない**（キーは jerseyNum/confidence/visibility/x/y のみ） | 「計算済みで入っている」✗ |
| `ballsSmoothed` | **dict**（`balls` は list） | 記載なし |
| ボール欠損 | 27.6% のフレームで `balls` が空 | 記載なし |

> **`speed` が無いのは設計に効く。** 速度が必要なら座標から求めることになるが、
> その際は平滑化窓を GSA の因果ラグより短く保つこと（`pitch_log_target_design`
> の実装制約 2）。

### 攻撃方向

`homeTeamStartLeft: true` は「**前半にホームが +x へ攻める**」を意味する。
3854 で検証：

- 前半 — 日本のシュートが x=+48.7 / 陣形重心 −12.5
- 後半 — 田中のゴールが x=−57.6（`shotOutcomeType=G`）、堂安が −37.7

`normalize()` がピリオドごとに符号を反転させ、**Home が常に x=1 へ攻める**
向きに揃える。変換後、田中のゴール時のボールは `x_norm = 0.970` になる。

## Task 3 — トラッキング品質の実測

**PFF は放送映像由来**なので、カメラがボールを追い、離れた選手は推定値になる。
`python -m pff.quality --game 3854` の結果（選手サンプル 26 万件）。

| 指標 | PFF | SkillCorner（公表値） |
|---|---|---|
| 試合全体の実測率 | **47.1%** | 51.2% |
| ボール欠損率 | 27.6% | — |
| confidence=LOW | 56.5% | — |

### ボールからの距離帯別 実測率

| 距離 | PFF | SkillCorner |
|---|---|---|
| 0–5m | **91.1%** | 87.0% |
| 5–10m | 88.4% | — |
| 10–15m | 87.2% | — |
| 15–20m | **83.1%** | 65.0% |
| 20–30m | 65.7% | — |
| 30–40m | **44.7%** | 27.9% |
| 40–50m | 29.1% | — |
| 50m+ | 13.7% | 7.9% |

**PFF は SkillCorner よりどの帯域でも良好。** 全体値が低く出るのは遠距離の
サンプルが多いため。

### 結論と推奨

**「オフボールの走り」を目的関数にする構想は、ボールから 20m 以内なら成立する**
（実測率 83% 以上）。崩しに絡む選手はこの範囲にいる。30m 超は推定値が主体に
なるため、そこを対象にした分析は避ける。

品質フィルタは **かけない**ことを推奨する。

1. `ESTIMATED` を落とすとフレームあたり 8 人が欠測になり、陣形や選手間距離が
   計算できなくなる
2. `confidence=LOW` が 56.5% あり、落とすと半分以上が消える
3. 距離帯で解釈を制御するほうが実態に合う（近距離は信頼、遠距離は参考値）

品質フラグは長形式に残るので、GSA 側で重み付けに使う道も残せる。

## Task 4 — 変換

```
PFF (29.97fps, 中心原点メートル)
  → pff.loader.normalize()      … 正規化 [0,1] ＋ 攻撃方向を Home→x=1 に統一
  → pff.convert.to_intermediate() … frame/time_sec/ball_x/Home_n_x… の横持ち
  → xt_pipeline_22              … assign_grid_and_xt_22 → extract_goal_window
                                   → reformat_to_22player_schema
                                   → add_zone_and_lbp_columns
  → Export_GSA CSV (126列)
```

**xT / GridID / ZoneID / LBP は自前で計算していない。** 既存 `xt_pipeline_22` が
すべて持っているため、その手前の中間形式を作るところだけを担当している
（既存資産と計算が食い違うのを避けるため）。

田中のゴール（3854 / eventTime 3215.15）で検証：

- **899 行 × 126 列**、サンプル CSV と**列名が完全一致**
- 最終フレームで `Ball_X = 0.972` / `Ball_xT = 1.0` → ゴールが再現されている
- 欠損率 2.4%、変換 14 秒

## ボールが記録されない区間について（重要）

**PFF はボールがデッドの間、追跡しない。** 田中のゴールを末尾にした窓で実測：

| 窓の長さ | ボール捕捉率 |
|---|---|
| 5 秒 | **100%** |
| 10 秒 | **100%** |
| 15 秒 | 80% |
| 20 秒 | 60% |
| 30 秒 | **40%** |

30 秒窓が 40% なのは、直前の約 20 秒がデッドタイム（イベントが 1 件も無い）
だったため。欠損は 2 区間に集中しており、長さは 309 フレーム（10秒）と
599 フレーム（20秒）。**この長さは補間で埋められない**（埋めれば存在しない
軌跡を作ることになる）。

### 対処

- `pff.convert.ball_coverage()` で **窓の長さごとの捕捉率を事前に確認**できる。
  アプリの①タブにも表示され、95% 以上を保てる最長の窓を推奨として出す。
- 1 秒以内の短い欠損だけは線形補間する。由来は `Ball_Source` 列に
  `measured` / `interp` / 空 で残る。
- **窓を短く取れば解決する。** 田中のゴールなら 12 秒窓で欠損 0%。

シーンを選ぶときは「ゴールの瞬間から遡って、プレーが途切れない範囲」を
取るのが原則。機械的に 30 秒にしないこと。

## 全指標の付与（`pff/enrich.py`）

Export_GSA（127列）に、GSA へ食わせる特徴量を付けて **425列** にする。

```python
from pff.enrich import enrich, feature_catalog
rich = enrich(df, fps)          # 425 列
cat  = feature_catalog(rich)    # 列の一覧（層・カテゴリ・欠損率）
```

### 3層構造を崩さない列設計

> **中間Y の計算元になった特徴を X 側に入れてはならない。**
> 入れると中間Y がその特徴の算術関数になり、行動→結果の因果ではなく
> 恒等式を学習してしまう。

接頭辞で層を明示している。GSA へ渡すときは接頭辞で選別すればよい。

| 接頭辞 | 層 | 列数 | 中身 |
|---|---|---|---|
| `X1_` | X 物理量 | 88 | 速度・加速度・スプリント判定・累積走行距離 |
| `X2_` | X 物理量 | 136 | ボール/ゴール/最近接相手との距離、半径 3/5/10m の相手数 |
| `X3_` | X 物理量 | 15 | 重心・幅・深さ・コンパクトネス・凸包面積・最終ライン |
| `X4_` | X 物理量 | 5 | 局所的な数的優位、アタッキングサードの人数 |
| `Y1_` | 中間Y | 17 | xT とその変化・累積・平滑・ピーク |
| `Y2_` | 中間Y | 24 | **ボロノイによる空間支配**（選手ごとの面積・チーム支配率） |
| `Y3_` | 中間Y | 6 | ボールの前進速度・進行距離、アタッキングサード/PA 侵入 |
| `Z_` | 最終Y | 3 | ゴールまでの残り時間・フレーム数、得点フラグ |
| `Q_` | 品質 | 4 | 追跡できた人数、ボールが実測か |

`Y2_`（空間支配）は **オフボールの動きが最も素直に効く指標**。走って空間を
作れば面積が増えるので、「オフボールの貢献を因果で説明する」という事業の
狙いに直結する。ラグビー側で実装済みの `rugby.voronoi` を流用している。

### データ辞書

`feature_catalog(df)` が **1 行 = 1 列** の対応表を返す。列名・層・カテゴリ・
対象・内容・単位・欠損率・値域が入っているので、そのまま指標選定に使える。
アプリの③タブから CSV でダウンロードできる。

### 出力は既定で全指標つき

①でシーンを読み込むと **その場で全指標まで計算**される。③タブの主たる
ダウンロードが `_enriched.csv`（425列）で、座標のみの 127 列は折りたたみの
中に置いてある。

速度は座標を微分して求める（PFF に `speed` は無いため）。平滑窓は既定
5 フレーム（0.17 秒）で、**GSA で読みたい因果ラグより短く**保っている。

## 既存パイプラインへの修正（2件）

どちらも **非整数 fps と欠測データで初めて露見**するもので、SkillCorner
（10fps・欠測なし）では起きなかった。

1. **`float()` が `pd.NA` で落ちる** — `add_zone_and_lbp_columns` 内の 8 箇所。
   選手が 1 人でも未追跡のフレームがあると LBP 計算が全面停止していた。
   `_f()` を追加して NaN に倒すよう修正。
2. **`extract_goal_window` が float を位置指定に渡す** — `window_sec * fps` が
   29.97 で 899.1 となり `iloc` が TypeError。`int(round(...))` に修正。

## モジュール構成

| ファイル | 役割 |
|---|---|
| `pff/paths.py` | 分割 ZIP を横断してファイルを解決 |
| `pff/loader.py` | メタ・ロスター・イベント・トラッキング読み込み、座標正規化 |
| `pff/convert.py` | 中間形式 → `xt_pipeline_22` → Export_GSA |
| `pff/scenes.py` | 解析候補シーンの一覧（ゴール・決定機・ライン突破） |

| `app_26.py` | シーンブラウザ（選択 → 俯瞰確認 → 書き出し） |

トラッキングは `bz2` のまま流し読みし、**指定区間を過ぎたら打ち切る**ので、
17 万フレームをメモリに載せることはない（30 秒窓の読み込みで約 13 秒）。
