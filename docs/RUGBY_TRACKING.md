# Pitch Log v25 — ラグビー上空映像トラッキング

トラッキングデータが存在しない競技（社内ラグビー部）向けに、**上空から撮影した
映像だけ**から選手の位置情報を復元し、フレームごとの時系列 CSV を作る仕組み。

サッカー側の Pitch Log は SkillCorner 等の既製トラッキングデータを入力にしていたが、
ラグビー部には映像しかない。そこで「映像 → 座標」の入口そのものを新規に作った。

---

## 全体像

```
動画 ──▶ ① キャリブレーション ──▶ ② 検出 ──▶ ③ 追跡 ──▶ ④ CSV 出力
         ピッチラインの交点を        動く点を     ID を維持    縦=時間
         クリックして画像↔m を        拾い出す     し続ける      横=選手
         対応づける
```

| `rugby/calibration.py` | ホモグラフィの推定・保存・適用、ピッチ枠の重ね描き | 1 |
| `rugby/detection.py` | 背景差分／YOLO による選手・ボール検出、ジャージ色抽出 | 1, 3 |
| `rugby/tracking.py` | ID を維持するマルチオブジェクト追跡、チーム分類 | 1, 3 |
| `rugby/pipeline.py` | 時間窓を指定した一括処理、座標平滑化 | 1 |
| `rugby/export.py` | ワイド／ロング／仕様書スキーマ CSV 出力 | 1 |
| `rugby/animate.py` | 2Dタクティカルマップ MP4 生成 | 2 |
| `rugby/physical.py` | 走行距離・速度・スプリント算出 | 4 |

画面に出す説明文はすべて `rugby/tutorial.py` に集約してある。文言だけ直したい
ときはこのファイルを編集すればよく、UI のコードに触れる必要はない。

見た目は `rugby/theme.py` に集約してある。パレット（`COLORS`）と芝のストライプ
定義（`turf_stripes`）は **Streamlit の CSS・Plotly のグラフ・書き出す MP4 の
3 か所すべてが同じ定義を参照**しているため、色を 1 か所変えれば画面も動画も
一緒に変わる。Streamlit の内部クラス名は版ごとに変わるので、セレクタは
`data-testid` を優先して使うこと。

### デザインの考え方（Modern Turf）

「ピッチログ」の名のとおり **上質な芝** をモチーフにしている。

- **面は深い緑、データは明るく。** 背景は `#071310`〜`#16362B` の暗いエメラルド。
  ピッチは 8m ごとの刈り込みストライプ（`#0E3A27` / `#134A32`）で質感を出す。
  UI を沈ませることで、選手・軌跡・数値だけが浮き上がる。
- **アクセントは 3 役に限定。** ゴールド `#FBBF24`（操作）／シアン `#22D3EE`
  （チームA）／コーラル `#FB7185`（チームB）。色数を絞ると視線が迷わない。
  彩度の高い原色は避け、Tailwind 系のフラットな色域から選んでいる。
- **視線導線。** 節見出しには短いゴールドのアクセントバーを添え、視線の起点を
  作る（`theme.section()`）。同じ役割の要素は必ず同じ形・同じ余白にして、
  目が形を再学習しなくて済むようにする。
- **立体感。** 選手のドットはフラットなまま、わずかなドロップシャドウで
  ピッチから浮かせる。ボロノイの塗りは alpha 0.25 に抑え、芝のストライプが
  透けて見える濃さに保つ。境界線は 1px の極細。
- **書体。** Inter を読み込み、取得できない環境ではシステムフォントに落ちる
  スタックにしてある。数値は `tabular-nums` で桁を揃え、比較しやすくする。

統合仕様書の原本は [`docs/Allclip_Tracking_Specs.md`](Allclip_Tracking_Specs.md)。

## 使い方

```bash
streamlit run app_25.py
```

操作に迷ったら、アプリ内の **「📖 使い方」タブ**に手順・症状別の対処・用語集が
入っている。各タブの冒頭にもそのタブ向けの折りたたみヘルプがある。

0. **📖 使い方** — 全体の流れ、手順、うまくいかないときの対処、用語集
1. **① 動画** — ファイルパスを入力（長時間の試合映像でよい）
2. **② キャリブレーション** — 3 通りある。黄色の枠が実際のラインと重なれば成功。
   結果は JSON に保存でき、同じカメラ位置の別映像で再利用できる。
   - **ピッチを 4 本の線で囲む（既定・かんたん）**: 外周に沿って 4 本引くだけ。
     どの線がどのラインかは傾きと位置から**自動判別**するので、名前の指定は不要。
     選ぶのは「囲んだ範囲」（デッドボールラインまで／ゴールライン間）の 1 つだけ。
     向きが逆に出たら反転チェックで直す。
   - **ラインを個別に指定**: ピッチが部分的にしか写っていない場合用。
     縦断 2 本以上＋横断 2 本以上をなぞり、それぞれの名前を選ぶ。
   - **点をクリック**: 交点を 1 つずつクリックして指定する（従来方式）。
3. **③ 区間解析** — 解析したい 30 秒を指定して実行
4. **④ 結果・背番号** — 2D マップで確認し、追跡 ID に背番号とチームを割り当てる。
   ボロノイ図（空間支配）の重ね表示も可能。
5. **⑤ フィジカル** — 走行距離・最高速度・スプリント回数。閾値は画面上で調整できる
6. **⑥ 2Dアニメーション** — タクティカルマップ MP4 の書き出し、空間支配率の推移
7. **⑦ CSV出力** — 縦=時間 / 横=選手 の CSV をダウンロード

CLI からも使える:

```bash
python -m rugby.make_synthetic --out synth.mp4 --seconds 20
python -m rugby.validate --video synth.mp4 --gt synth.groundtruth.csv --duration 10
python -m rugby.animate --csv tracks_long.csv --out tactical.mp4 --trail 30 --voronoi
```

## 出力フォーマット

列名は既存 Pitch Log の `Export_GSA` と同じ規約なので、そのまま既存の可視化・
特徴量付与パイプラインに載せられる。

**ワイド形式**（主たる納品物・縦軸=時間 / 横軸=選手）

| Frame | Video_Frame | Time | Home_P1_X | Home_P1_Y | Home_P1_Speed | … | Away_P15_Y |
|---|---|---|---|---|---|---|---|

- `_wide_meters.csv` … 実寸メートル（分析向き）
- `_wide_normalized.csv` … 0–1 正規化（既存 Pitch Log 互換）
- `_tracks_long.csv` … 1 行 = 1 選手 1 フレーム（生データ）

背番号を割り当てると列名がその番号になる（未割当なら出現の長い順に P1, P2…）。

## 設計上の要点

### 追跡はピッチ座標（メートル）で行う

検出は画像座標で行うが、ホモグラフィで即座にメートル系へ落としてから追跡する。
これにより

- **速度ゲートが物理的に意味を持つ**（人は 11 m/s を超えない）
- 選手の見かけサイズが画面内の位置によらず一定になる
- 遮蔽中の予測が実距離で評価できる

画像座標のまま追跡すると、画面の手前と奥でスケールが違うため、これらの制約が
一切使えない。

### 遮蔽（選手の重なり）への 4 段構え

1. **物理速度ゲート** — ありえない移動量の対応づけを除外
2. **カルマン予測** — 見失っている間も等速モデルで位置を保持
3. **見た目の再同定** — ジャージ色の HSV ヒストグラムを EMA で保持
4. **チーム拘束** — 別チームの検出には乗り換えにくくする

さらに **マッチングカスケード**（DeepSORT と同方式）を採用している。全トラックを
一度に Hungarian へ通すと、長く見失って位置が不確かなトラックが「全体コストの
最小化」の名目で正しいトラックから検出を奪い、ID の分裂を大量に生む。直近に
更新されたトラックから順に検出を確保することでこれを防いでいる。

### 密集塊の分割は実測面積から自己較正する

単独の選手が占める面積は、輪郭・影・アンチエイリアスの分だけ幾何計算値より
大きくなる（検証では約 1.8 倍）。閾値を幾何推定のまま使うと **2 人が重なった塊が
「1 人」として通過し、必ず片方のトラックが失われる**。毎フレームの面積分布の
中央値を「単独選手 1 人ぶん」とみなして較正することで、重なりを正しく分割する。

### 速度は位置とは別に平滑化する

カルマンの速度状態は、位置追従を優先すると必然的にノイジーになる。そこで速度は
出力位置の平滑微分（既定 5 フレーム窓）で求め直している。

> **注意**: この平滑窓は、GSA で読みたい因果ラグより十分短く保つこと。
> 平滑窓がラグを超えるとラグ構造が消える（`pitch_log_target_design` の実装制約 2）。

## 精度（合成映像・正解座標つき）

`rugby/make_synthetic.py` が生成した 20 秒・30 人・25fps・1280×720 の映像で測定。

| 指標 | 値 |
|---|---|
| キャリブレーション再投影誤差 | 0.000 m |
| 検出率 | 98.9% |
| 位置誤差（中央値） | **0.086 m** |
| 位置誤差（90 パーセンタイル） | 0.125 m |
| 単一 ID での被覆率（平均） | **99.3%** |
| 1 選手あたりのトラック数 | 1.07（理想 = 1.00） |

合成映像は理想条件（背景が静止、選手が単色の円）なので、**実映像ではこれより
悪化する**。実際のラグビー部の映像で再測定し、③の「観測ノイズ」「想定加速度」
「選手の想定サイズ」を調整する前提。

### 条件別の耐性テスト

`rugby/make_synthetic.py` に人数・交錯・俯角・手ブレを振るオプションを追加し、
12秒・25fps の映像で 8 秒窓を解析して測定した結果（`--motion crossing` は
左右から直進させて中央で密に交錯させる過酷条件）。

| 条件 | 物体数 | 検出率 | 誤差med(m) | 誤差p90(m) | 単一ID被覆 | 分裂/人 | track数 | 秒/200f |
|---|---|---|---|---|---|---|---|---|
| 基準・ランダム・俯瞰 | 30 | 0.977 | 0.089 | 0.133 | 0.983 | 1.13 | 32 | 14.1 |
| 高密度 | 50 | 0.965 | 0.088 | 0.139 | 0.940 | 1.36 | 59 | 14.0 |
| 高密度 | 80 | 0.963 | 0.089 | 0.147 | 0.926 | 1.35 | 95 | 18.1 |
| 密に交錯 | 30 | 0.991 | 0.088 | 0.131 | 0.980 | 1.20 | 35 | 11.7 |
| 密に交錯 | 50 | 0.982 | 0.089 | 0.141 | 0.923 | 1.52 | 63 | 13.9 |
| 真俯瞰 (perspective=0) | 30 | 0.984 | 0.085 | 0.129 | 0.981 | 1.13 | 30 | 11.7 |
| 斜め (perspective=0.35) | 30 | 0.965 | 0.099 | **0.245** | 0.970 | 1.23 | 34 | 12.2 |
| 手ブレ6px・**補正なし** | 30 | 0.980 | **0.721** | 1.034 | **0.817** | **5.67** | **676** | 97.7 |
| 手ブレ6px・補正あり | 30 | 0.989 | 0.086 | 0.138 | 0.993 | 1.07 | 34 | 23.6 |

読み取れること:

- **位置誤差は条件によらず約 0.09m で安定**している。悪化するのは ID の維持率のほう。
- **80 物体まで実用的に動く**（単一ID被覆 0.983 → 0.926）。ラグビー30人は余裕がある。
- **密な交錯はほとんど効かない**（30物体で被覆 0.980）。遮蔽対策が機能している証拠。
- **斜め映像では p90 誤差がほぼ倍**（0.133 → 0.245m）。遠方の物体ほど 1px の実距離が
  大きくなるため。中央値は保たれるので、外れ値の扱いに注意すればよい。
- **手ブレを補正しないと壊滅する**（トラック 34 → 676本、分裂 5.67倍）。
  ドローン・手持ち撮影では必ず「手ブレ補正」を有効にすること。処理時間は約 2 倍。

### 4 本で囲めばラインの名前は要らない

ピッチ外周を 4 本の線で囲んだ場合、どの線がどのラインかは幾何学的に決まる。

1. 各線の傾きから**縦向き 2 本・横向き 2 本**へ振り分ける
2. 交点 4 つを求める
3. 重心まわりの偏角で環状に並べ、左上に最も近い点を先頭に回す
4. 隣接辺の向き（横長のほうが「右上」へ向かう辺）で回り方を決める

これで「左上 → 右上 → 右下 → 左下」が確定し、ピッチの四隅と対応づく。
**線を引く順番も向きも問わない**（検証済み）。

> 画像の左右・上下がピッチのどちら向きかはカメラ設置次第で決まらないため、
> そこだけは反転チェックで指定する。重ね描きを見れば一目で分かる。

> ⚠ 実装時、画像座標は Y が下向きなので**多角形の巻き方向の判定が反転する**。
> 符号付き面積で判定すると対角が入れ替わり、往復誤差が 11m 出た。
> 辺の向き（横長か縦長か）で判定するよう修正済み。

### キャリブレーションは点より線のほうが正確

交点を 1 点ずつクリックするより、ラインをなぞって**その交点を計算する**ほうが
精度が出る。理由は 3 つ。

1. 線は長く取れるので、端点が数ピクセルずれても線の**向き**への影響が小さい。
   交点は 2 本の線全体の情報から決まる。
2. ピッチの隅が画面外・選手で隠れていても、線を延長した交点として計算できる。
3. 交点が自動的に増える。縦断 3 本 × 横断 2 本をなぞれば 6 交点が得られ、
   RANSAC で外れ値を吸収できる。

> ⚠ **4 点ちょうどでは再投影誤差は必ず 0.000 になる**（4 点はホモグラフィを
> 一意に決めるため、常に完全一致する）。つまり最小構成では誤差表示が品質の
> 指標にならない。線を 1 本足して 6 交点にすると、初めて実際のずれが見える
> （検証では端点に 1px のノイズで 0.055m、3px で 0.430m と出た）。

### 手ブレ補正はキャリブレーションを取ったフレームへ揃える

上の耐性テストで見つかった問題。手ブレ補正の基準を「解析窓の先頭フレーム」に
していたところ、そのフレーム自体のブレ量ぶん座標が丸ごとオフセットし、
**6px のブレで 0.7m の系統誤差**が出ていた。

`Calibration.ref_time_sec`（クリックしたフレームの時刻）を保持し、補正時は
そのフレームへ揃えるよう修正。誤差は 0.721m → **0.086m** となり、無風条件と
同一水準に戻った。ピッチ座標系の原点はキャリブレーションを取った瞬間の見え方で
決まるので、揃える先もそこでなければならない。

---

### フィジカル算出は「区間」に割ってから微分する（モジュール4）

速度・距離を出すときの最大の敵は検出枠のジッターだが、それ以上に効くのが
**ID の取り違えと欠測**である。トラックが別の選手へ飛び移ると、その 1 フレームで
数メートル移動したことになり、最高速度が数十 km/h に化ける。

そこでトラックを次の 2 条件で区間に割り、区間ごとに独立して微分している。

1. 物理的にありえない変位（`max_speed_mps` 超え）＝ ID 取り違えの疑い
2. フレームの欠測 ＝ その間に何が起きたか分からない

検証では、この処理の有無で最高速度が **37.0 km/h → 20.2 km/h**（正解 15.5 km/h）
と変わった。レポートには `discontinuities`（断絶回数）列を出しているので、
値が大きい選手は数値を疑うこと。

### ボロノイ図はピッチ矩形でクリップする（モジュール5）

`scipy.spatial.Voronoi` は外周の母点に対して無限遠へ伸びる領域を返すため、
そのままでは描画も面積計算もできない。ここでは**母点をピッチ外側へ鏡像反転させて
追加**することで元の母点の領域をすべて有界にし、そのうえで shapely でピッチ矩形と
論理積を取っている。検証ではセルの合計面積がピッチ面積（7000 m²）と一致し、
支配率の合計も 1.0000 になることを確認済み。

## 既知の限界

### ボール検出は現状うまくいかない ⚠

上空映像でのボールは十数ピクセル以下しかなく、背景差分では芝のノイズと大きさで
区別できない。合成映像での検証では、拾えた候補の位置誤差が**中央値 15m 超**で
実用にならなかった。誤った座標を出すと下流の分析を壊すため、**既定では無効**に
してある（UI の「ボールも検出する（実験的）」で有効化できるが要目視確認）。

現実的な選択肢:
- `backend="yolo"` を高解像度映像に対して使う（sports ball クラス）
- 手動アノテーション
- ボール保持者（キャリア）だけを人手で指定する

### 背番号の自動認識は未対応

俯瞰視点では背番号の文字が小さすぎて OCR が安定しない。現状は **UI で追跡 ID に
背番号を手動割当**する方式。一度割り当てればその ID の全フレームに反映される。

### 仕様書との差異（意図的な判断）

| 仕様書 | 本実装 | 理由 |
|---|---|---|
| BoT-SORT / ByteTrack（supervision） | 自前の追跡器（カスケード＋Re-ID） | 追跡を**ピッチ座標(m)で行う**ため。既製実装は画像座標前提で、物理速度ゲートが使えない。YOLO バックエンドは併存 |
| 接地点＝枠の底辺中央 | 俯角に応じて自動選択 | **真俯瞰では底辺中央は誤り**。真上からは足元も頭も同じ位置に写り、枠の底辺は体の手前側の縁にすぎず、体半分ぶん系統的にずれる。斜め映像では仕様どおり底辺中央を使う |
| 座標平滑化は必須 | 既定オフ（`smooth_positions=0`） | カルマンで既に平滑化済み。二重にかけると加減速が鈍る。実写で生検出が荒い場合に有効化する |
| スプリント閾値 24km/h | 既定 24km/h（UI で変更可） | サッカー基準。ラグビーでは 20km/h 前後で運用することもあるため可変にした |

### その他

- 静止し続ける選手は背景差分では検出できない（YOLO バックエンドなら可）
- カメラが動く場合は「手ブレ補正」を有効にする（処理時間は約 2 倍）
- `③ interline`（DF-MF-FW のライン間）は役割情報が必要なため未対応
